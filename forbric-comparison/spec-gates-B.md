# SPEC 闸门核验 B

`producedBy: lane_b`

## 0. 核验范围与口径

- 核验对象：`SPEC.md` §0（第 13–47 行）与 §5（第 919–948 行）；共享约束取自根目录 `AGENTS.md`，并核对 `PROGRESS.md` 顶部第三十步记录。
- 本轮只做规范核验。没有修改 `SPEC.md`、`SPEC.zh-CN.md` 或任何其他受保护文件，没有读取 `src/`，没有运行构建、测试或 Minecraft，没有产生对照数字。
- “扩成加载器”按需要参与运行时加载这一含义评估：不仅是给现有静态分析器增加“加载器”名称，而是可能加载类、处理 Mixin 或字节码，并实际启动 Minecraft。若最终只做离线对照器，下表中所有“必须改”都不应自动执行，应先改回离线范围。
- 判定分三类：**必须改**表示该条款按字面与运行时加载器直接冲突；**可保留**表示不因加载器扩展而自然失效；**需用户裁决**表示是否需要该能力尚未被需求定义，不能由实现者顺手扩边界。

## 2. §5 逐条闸门

| ID | 位置 | 原文要点 | 判定 | 理由与影响 |
|---|---|---|---|---|
| S5-01 | `SPEC.md:921-922` | 使用 SLF4J facade + Log4j2，并定义 `ERROR` / `WARN` / `INFO` / `DEBUG` / `TRACE` 五级 | **可保留** | 这是观测与失败落账接口，不限制加载器是否需要 ClassLoader。若将来运行在被宿主管理的进程内，日志实现仍需做依赖冲突评审，但当前规范不必先改。 |

## 3. 两条特别原文

### 3.1 “不启动 Minecraft”

`AGENTS.md:17` 的逐字原文：

> 不启动 Minecraft、不加载类、不解析 class 文件、不处理 Mixin、不改写字节码。

`SPEC.md:15` 的英文原文：

> M0 **does not start Minecraft, does not load classes, does not process mixins, does not rewrite bytecode**.

`SPEC.md:19-20` 还有 M1 的原文：

> It does not start Minecraft either, does not load classes, does not read class files…

结论：扩展成实际加载器时，不能靠解读“加载器”三个字绕过上述三处；它们必须作为 §0 scope 变更的一部分，经用户明确批准后同步改写两种 SPEC。

### 3.2 “不引 MC/加载器依赖”

在本次授权范围内，能逐字定位到的原文只在 `AGENTS.md:18`：

> 不引入 Minecraft / Fabric Loader / Forge / NeoForge / Mixin / ASM 依赖。

`SPEC.md` §0 与 §5 中没有这一句或等价的全依赖清单。§0 只写了两条相邻但不完全等价的排除项：

> - Any ClassLoader, JVM agent, or bytecode manipulation (ASM / Mixin / Tiny Remapper)
> - Any Minecraft launch, download or patching logic

定位缺口必须如实保留：`AGENTS.md:15` 写“以 `SPEC.md` §0 与 §5 为准，摘要如下”，但“不引入 Minecraft / Fabric Loader / Forge / NeoForge / Mixin / ASM 依赖”在 §0/§5 中没有逐字落位。下一闸门需要先决定是把该禁令正式补入 SPEC，还是按用户确认后的运行时范围改写它；本轮不得自行选择。

## 4. 汇总与下一道闸门

### 必须改

- 要让项目真正承担运行时加载职责，至少 S0-01、S0-02、S0-03、S0-04、S0-07、S0-14 与 S0-15 中的“Minecraft launch”部分必须进入 §0 变更草稿。
- S0-05 的字节码改写与 S0-15 的“download / patching”必须单独裁决，不能把“加载器”解释成自动允许全部三项。

### 可以保留

- 静态发现、元数据、依赖与环检测仍可保留为加载前分析阶段（S0-06、S0-07 的分析部分、S0-11）。
- 声明性冲突与行为性冲突的诚实边界（S0-10、S0-12、S0-13）应保留。
- 跨加载器互操作、GUI、配置器、安装器、自动兼容/修复及顺序输出禁令（S0-16 至 S0-19）均不应被“对照基线”自动解锁。
- §5 的日志级别与八条硬规则整体可保留；若新增长期运行时错误，必须用新的事件分类扩展，不能改写既有解析失败口径。

### 需用户裁决

- “加载器”是否指实际启动 Minecraft、执行 ClassLoader 的运行时实现，还是只是一个离线对照框架。
- 是否支持 Mixin、是否自持 bytecode transform、是否允许下载或修补游戏文件。
- 运行时失败与现有“一个 jar 至多一条 ERROR”如何分账。
- `AGENTS.md:18` 的依赖禁令以何者为准、如何在 SPEC 补位。

### 下一道闸门

**待裁决：是否改 `SPEC.md` §0（并同步 `SPEC.zh-CN.md`）。**

本轮不改。用户点头前也不应写 §0 替代文本、改 `AGENTS.md`、进入 M2、实现 ClassLoader 或启动 Minecraft。建议先只裁决“实际运行时加载器 / 离线对照器”这一产品范围，再授权 SPEC 双版同步草拟。
